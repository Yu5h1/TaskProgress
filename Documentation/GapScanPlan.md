## 系統階層與關係

```text
TaskProgress 可執行項目流程（task-progress-items）
├─ 缺口盤點（本計畫新增）：找出還沒人排定的缺口 → 一份決策題，由使用者選
│     ↓ 使用者選定的缺口成為規格目標、計畫段落或卡片
├─ 退場盤點（本計畫新增）：找出不該再做的待處理子項 → 決策題，由使用者確認
│     ↓ 確認後封存並寫明退場理由，handoff 記一條已排除方向
├─ 評估（plan）：只找已排定、已定案的工作 → 子項、決策題、Next
├─ 執行（run）與驗收（accept）
└─ 既有來源：handoff、Requirements、規格目標、現有子項、決策檔
```

缺口盤點找「還缺什麼」，退場盤點找「已經不該做什麼」，兩者都只提出候選；評估負責「已決定要做的，拆成可執行的子項」。分開，是因為做什麼、不做什麼都由使用者決定。

## 問題與目標

**問題。** 用 `/task-progress-items` 評估時，agent 只會從已經排定的工作裡找項目，不會發現專案還缺什麼。例如 Web 有某個功能、UX 還沒有對應規格，除非使用者明確說「把 ## 整合進 UX」，否則沒有人會提出；就算寫出規格，也不會自動有任務卡和子項，要再評估一次才會出現。

**目標。** 提供一個盤點步驟，從計畫目標、規格與各平台實作、其他專案提出的需求等來源找出缺口，整理成使用者可以選的候選；使用者選定後，接上現有的「評估 → 執行 → 驗收」流程。

另一方面，評估也不會發現既有子項已經沒有意義：目標已被別的項目達成、前提已改、設計被推翻，子項仍留在待處理，佇列照樣會挑它（使用者 2026-10-24 提出）。

**目標（退場）。** 再提供一個退場盤點：找出不該再做的待處理子項，交給使用者確認後退場，並留下理由，避免之後的 agent 重新提出。

**明確非目標。** 兩種盤點都不自行建立子項、封存子項、設定 Next 或開始任何工作；決定權在使用者。

## 現況（2026-10-24）

- **評估刻意不找新工作。** agent-executable-items〈Evaluate a scope〉第一句：評估只找已排定、已定案的工作，不找 agent 自己想做的工作。讀的來源是 handoff 的下一步與待決、Requirements、規格目前的目標、friction log、現有子項與決策檔。
- **缺口發現只有一個零散入口。** cross-platform-module-spec〈Select scope〉的「整個庫的候選盤點」：列一張表（能力、使用情境、實作證據、現有涵蓋、相依、建議範圍），等使用者選。限制：
  - 只涵蓋跨平台模組；規格只做到一半、某平台還沒實作、計畫目標沒人負責等缺口不在範圍內。
  - 結果是對話裡的一張表，選定後寫進擁有者的計畫，不產生決策題、卡片或子項。
  - 不能從 task-progress-items 啟動，要另外下「把 ## 整合進 UX」。
- **選定後的銜接已經存在。** 規格目標一旦寫好，評估會讀到「規格目前的目標」並建立子項；scope 沒有對應卡片時，評估會為這項工作建一張卡。
- **一般子項沒有退場路徑。** 評估對既有子項只規定「不重建」；只有「問題：」子項會被評估轉成修正、決策題或已排除方向。task-progress-report 規定 `archive` 只用於明確的退場決定，agent 不能自行封存。
- **退場理由沒有地方放。** `archive` 同時代表「留作歷史」與「不做了」，Report 上分不出正常收尾和被推翻。實例：`next-marker › next-edit-mode` 由使用者決定不需要後封存；頂端 Next 面板被推翻只記在 handoff 的已排除方向；handoff 裡「先修正既有項目的狀態推算」在項目完成後仍留著。

## 設計（草稿）

對應〈尚未決定〉的選項。

- **入口。** task-progress-items 新增一個動詞（名稱待決），例如 `/task-progress-items scan [scope|all]`。
- **來源。** 依盤點範圍（待決），候選來源包括：計畫目標與實際實作的落差；規格的目標與各平台實作的落差（哪個平台還沒做、做到哪一版）；其他專案對本專案提出、仍未處理的 Requirements；跨平台模組候選（某平台已有、規格擁有者還沒有）。
- **產出。** 每個候選附上證據（檔案、呼叫點、現有涵蓋）與建議；寫成一份決策題，綁在 scope 的一張卡片上，使用者在決策頁選。
- **選定之後。** 被選中的缺口寫成規格目標、計畫段落或卡片；下一次 `plan` 照現行評估規則拆成子項。跨平台模組候選選定後，照 cross-platform-module-spec 撰寫規格。
- **退場盤點。** 評估（或盤點動詞）檢查每個待處理子項，有下列證據時列為退場候選：目標已由別的項目或設計達成；規格或計畫改了，前提不成立；handoff 的已排除方向已涵蓋它；它依賴的設計被推翻。候選寫成決策題，因為退場改變要做什麼，不屬於可照建議直接作答的低風險題。
- **確認之後。** 子項退場（狀態形式待第 7 題），活動紀錄寫明類別與理由（例如「被推翻：設計錯誤」「沒必要：目標已由某項達成」）；依 [AgentArtifactGuide〈Retiring a design〉](../../.agents/AgentArtifactGuide.md#retiring-a-design) 在 handoff 的已排除方向記一條。
- **與〈目標與流程〉的關係（2026-10-24）。** 「一次只進行一個模組、下一個由使用者點名」已取消；[AcceptanceChainPlan〈目標與流程〉](AcceptanceChainPlan.md#目標與流程)改為：從已確認目標推得出的工作直接建立，會設定或改變目標的才交給使用者。第 3～6 題的前提因此改變，作答前先修訂。
