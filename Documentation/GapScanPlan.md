## 系統階層與關係

```text
plan（每一層做同一件事：對照這一層的目標）
├─ 缺口盤點：目標需要、但還沒有的工作
│     ├─ 目標推得出的 → 直接建立卡片或子項，寫明服務目標的哪一句
│     └─ 會擴充或改變目標的 → 決策題
├─ 退場盤點：已經不該做的待處理子項 → 決策題，由使用者確認
│     ↓ 確認後退場並寫明理由，handoff 記一條已排除方向
└─ 既有工作：handoff、Requirements、規格目標、現有子項、決策檔
```

缺口盤點找「還缺什麼」，退場盤點找「已經不該做什麼」。兩者不是獨立的動詞，是每一層 plan 的一部分：scope 層對照專案目標產出卡片，卡片層對照卡片目標產出子項。

## 問題與目標

**問題。** 用 `/task-progress` 評估時，agent 只會從已經排定的工作裡找項目，不會發現專案還缺什麼。例如 Web 有某個功能、UX 還沒有對應規格，除非使用者明確說「把 ## 整合進 UX」，否則沒有人會提出；就算寫出規格，也不會自動有任務卡和子項，要再評估一次才會出現。

**目標。** plan 從計畫目標、規格與各平台實作、其他專案提出的需求等來源找出缺口，依〈目標與流程〉的分界直接建立或交給使用者，接上現有的「評估 → 執行 → 驗收」流程。

另一方面，評估也不會發現既有子項已經沒有意義：目標已被別的項目達成、前提已改、設計被推翻，子項仍留在待處理，佇列照樣會挑它（使用者 2026-10-24 提出）。

**目標（退場）。** 找出不該再做的待處理子項，交給使用者確認後退場，並留下理由，避免之後的 agent 重新提出。

**明確非目標。** 退場不由 agent 自行執行，一律經使用者確認；會擴充或改變目標的缺口不由 agent 自行建立。

## 現況（2026-10-24）

- **評估刻意不找新工作。** agent-executable-items〈Evaluate a scope〉第一句：評估只找已排定、已定案的工作，不找 agent 自己想做的工作。讀的來源是 handoff 的下一步與待決、Requirements、規格目前的目標、friction log、現有子項與決策檔。
- **缺口發現只有一個零散入口。** cross-platform-module-spec〈Select scope〉的「整個庫的候選盤點」：列一張表（能力、使用情境、實作證據、現有涵蓋、相依、建議範圍），等使用者選。限制：
  - 只涵蓋跨平台模組；規格只做到一半、某平台還沒實作、計畫目標沒人負責等缺口不在範圍內。
  - 結果是對話裡的一張表，選定後寫進擁有者的計畫，不產生決策題、卡片或子項。
  - 不能從 task-progress 啟動，要另外下「把 ## 整合進 UX」。
- **選定後的銜接已經存在。** 規格目標一旦寫好，評估會讀到「規格目前的目標」並建立子項；scope 沒有對應卡片時，評估會為這項工作建一張卡。
- **一般子項沒有退場路徑。** 評估對既有子項只規定「不重建」；只有「問題：」子項會被評估轉成修正、決策題或已排除方向。task-progress-report 規定 `archive` 只用於明確的退場決定，agent 不能自行封存。
- **退場理由沒有地方放。** `archive` 同時代表「留作歷史」與「不做了」，Report 上分不出正常收尾和被推翻。實例：`next-marker › next-edit-mode` 由使用者決定不需要後封存；頂端 Next 面板被推翻只記在 handoff 的已排除方向；handoff 裡「先修正既有項目的狀態推算」在項目完成後仍留著。

## 已決定

2026-10-24 依〈目標與流程〉作答，第 3、7 題由使用者決定（[gap-scan.decisions](../decisions/gap-scan.decisions)）：

- **第 1 題：範圍。** 完成專案目標需要的任何工作都在範圍內：模組、規格、平台實作、計畫目標、文件、驗證，不限程式開發；程式品質類（測試缺口、TODO、過時文件）只在目標需要時列入。
- **第 2 題：跨 scope。** `plan all` 跨所有 scope，每個 scope 只做淺層盤點（缺口、退場候選、Next），往下拆只對指定的範圍。
- **第 3 題：流程與方法的分工。** 候選盤點的方法（怎麼盤點候選模組、什麼算一個模組、要看哪些證據）是 UX 的方法，留在 spec-author；plan 在 UX scope 找缺口時照它做，產出照〈目標與流程〉處理。spec-author 只拿掉流程規則：「等使用者選」改照〈目標與流程〉的分界，通用的確認目標改為引用 task-progress。
- **第 4 題：產出。** 目標推得出的缺口直接建成卡片或子項，寫明服務目標的哪一句；會擴充或改變目標的寫成決策題。
- **第 5 題：落點。** 缺口在 scope 層成為卡片（目標引用專案目標的那一句），在卡片層成為子項；卡片在下一次 plan 到它、或本次範圍包含它時拆成子項。
- **第 6 題：入口。** 不新增動詞；盤點是每一層 plan 的一部分。
- **第 7 題：退場狀態。** 新增兩種狀態，不沿用 `archive`：
  - `obsolete`（被取代）：目標已由別的子項或設計達成；必須指向取代它的那一個，意思同 C# 的 `[Obsolete]`。
  - `discontinued`（棄案）：前提不成立、設計被推翻、不再發展；必須寫理由。

  `archive` 回到只代表「完成後留作歷史」。

## 設計

- **來源。** 計畫目標與實際實作的落差；規格的目標與各平台實作的落差（哪個平台還沒做、做到哪一版）；其他專案對本專案提出、仍未處理的 Requirements；某平台已有、規格擁有者還沒有的能力。
- **證據。** 每個缺口附上證據（檔案、呼叫點、現有涵蓋）。缺口只從目標寫明的服務對象取證，不從其他模組的相似介面推論。
- **退場盤點。** plan 檢查範圍內每個待處理子項，有下列證據時列為退場候選：目標已由別的項目或設計達成；規格或計畫改了，前提不成立；handoff 的已排除方向已涵蓋它；它依賴的設計被推翻；目標改了之後對不上新目標。候選寫成決策題，因為退場改變要做什麼。
- **確認之後。** 依證據把子項改成 `obsolete`（指向取代者）或 `discontinued`（附理由）：「目標已由別的項目或設計達成」屬於前者，「前提不成立」「設計被推翻」「已排除方向涵蓋」屬於後者；依 [AgentArtifactGuide〈Retiring a design〉](../../.agents/AgentArtifactGuide.md#retiring-a-design) 在 handoff 的已排除方向記一條。
- **收尾檢討。** 卡片的收尾檢討（〈目標與流程〉）也做一次缺口與退場盤點，對照整張卡的目標。
