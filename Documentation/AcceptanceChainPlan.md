# 驗證流程選項：`[acceptance]` 與 `[manual]`

> Task ID: checklist-acceptance-chain

Report：task-progress › agent-workflow。

一個可執行項目綁定一份 checklist。checklist 裡有哪些檢查標籤，就決定這個項目要經過哪些驗證；子項的狀態從 checklist 推算出來，不另外存：

```text
執行者跑完自己的檢查（不標）
├─ 有 [acceptance] → 另一個 agent 驗收
└─ 有 [manual]     → 使用者驗收
全部 [x] → 子項顯示完成
```

改任何規則前，先照〈流程紀錄〉的情境重走一遍，確認沒有規則互相衝突。

## 為什麼

Agent 自己寫步驟、自己執行時，交給更高階的模型驗收後，約兩成項目是做錯或沒對齊需求意圖（不是沒做）。Report 目前分不出「執行者做完」和「驗收通過」，做錯的項目看起來和完成的一樣。高階模型多半能在執行時自行驗收通過，所以獨立驗收是可選的，不是每一項都要。

這套流程會長期使用，每條規則都以兩個標準判斷（使用者 2026-10-22）：

- **有效**：任務更對齊、完成度更有保證；零散的任務能歸類、流程化、可追蹤。
- **高效**：agent 用這套流程就能和使用者對齊任務，減少反覆詢問目前狀態與流程；子項之間以連結互相指向，依賴的任務一點就到。

## 目標與流程

使用者於 2026-10-24 決定這一節的內容；判斷依據是〈為什麼〉的有效與高效。細節題目在 [goal-flow.decisions](../decisions/goal-flow.decisions)，七題都已答。

**原則。** 這套流程讓 agent 盡可能理解目標、跑完任務，交出使用者想要的結果。使用者只在開頭確認目標、最後驗收；中途修改與討論是使用者的選擇，不算 agent 的錯。重做是正常的完成方式：很多事沒有經驗，無法一次到位。

### 分工

| 誰 | 負責 |
|---|---|
| 使用者 | 確認目標；驗收結果；結果沒對齊時判斷是做錯了（驗收不通過，重做），還是目標錯了（修改目標） |
| agent | 目標與驗收之間的一切：評估可行方案、列步驟、建立子項、執行、自驗、他驗、記錄經驗 |

```text
使用者：確認目標
  ↓
plan：評估可行方案 → 列步驟 → 依類型建立子項
auto：plan → 執行 → 自驗 → 他驗
  ↓
使用者：驗收；沒對齊時重做，或修改目標後重新 plan
```

### 釐清目標

最該先做的一步。目標設錯，後面每一步做得再好都是白費：任務完成了，使用者才發現不是他要的，或有一條成本低得多的路。〈為什麼〉的兩成「沒對齊需求意圖」屬於這一類；頂端 Next 面板做完當天被刪除、Configuration 規格到採用時才發現草稿、重試、套用只是 Web 非同步儲存的需要，都是目標沒先對齊的代價。

- **什麼時候做。** 建立卡片或子項之前，目標還沒寫下或沒經使用者確認時。目標已經寫好並確認過（規格的〈目標〉、計畫的〈問題與目標〉），引用它，不再問。
- **要釐清什麼。** 真正的意圖（要解決什麼問題；指令描述的是做法時，先問它要達成什麼）；完成的樣子（可觀察的結果，之後成為驗收條件）；不做什麼；目標本身對不對（是否已有機制做到、有沒有更小的改動、是不是只處理了表面症狀，有破綻就在第一次回覆指出）。
- **怎麼問。** 查得到的先查；查不到的一次問一題，附建議答案，依相依順序問（[task-progress-items〈Resolve the target〉](../.agents/skills/task-progress-items/SKILL.md#resolve-the-target)的「方向不清」一段，範圍從「方向不清時」擴大為「建立工作之前」）。跨平台模組已有同樣的步驟：[cross-platform-module-spec〈Define the goal before the specification〉](../../.agents/skills/cross-platform-module-spec/SKILL.md#define-the-goal-before-the-specification)。
- **寫在哪裡（第 1 題）。** 卡片計畫文件的〈問題與目標〉，卡片摘要連結它；沒有計畫文件的卡片，寫在子項 checklist 的開頭說明。

目標分層：專案目標（plan.md）→ 卡片目標 → 子項結果。下一層的工作都要能指出它服務上一層目標的哪一句。

### 每一層的 plan

plan 在每一層做同一件事：對照這一層的目標，看下一層已有什麼、缺什麼、什麼已經不該做。

| 層級 | 對照的目標 | 產出 |
|---|---|---|
| scope | 專案目標 | 任務卡，依規模與類型分組；完成專案需要的任何工作都算，不限程式開發 |
| 任務卡 | 卡片目標 | 子項，依〈子項類型〉建立；缺的補上，對不上目標的列為退場候選 |
| 子項 | 子項結果 | 只有執行與驗收；子項本身不清楚時，出決策題或在對話中和使用者定案 |

- **直接建立，還是交給使用者。** 從已確認的目標推得出來的工作（要完成目標就一定要做），直接建立，寫明服務目標的哪一句（第 2 題）；寫不出來，就表示它在擴充或改變目標，寫成決策題。例子：Web 的設定面板有「匯入／匯出」、UX Configuration 沒有；Configuration 目標寫明的服務對象需要它，就直接建立，沒有就出決策題。
- **`plan all`。** 跨所有 scope，但每個 scope 只做淺層盤點（缺口、退場候選、Next），不往下拆；往下拆、往下做只對指定的範圍。
- **目標改了之後。** 使用者修改卡片目標 → 重新 plan 那張卡 → 對不上新目標的子項列為退場候選，缺的補上。
- **專案分析。** scope 層的分析在專案目標改變時做一次，結果存成卡片；不要每次 plan 都重做。資源、技術能力等估計，只在會改變使用者的決定時才做。
- **平行。** 多個模組、多張卡可以同時推進；兩項工作能不能同時做，依它們會改到的檔案與共用資源判斷（[WorktreeReportPlan](WorktreeReportPlan.md)）。原本「一次只進行一個模組、下一個由使用者點名」的規則已取消（使用者 2026-10-24：那是 2026-10-14 的試跑被擴大成長期規則）。

**流程與方法分開。** 任務流程（釐清目標、每一層 plan 對照目標找缺口並決定直接建立或出題、拆解、驗證、驗收）歸 task-progress-items；某個領域怎麼找缺口、怎樣才算做對（例如 UX 的候選模組盤點與規格寫法）歸該領域的技能。plan 在某個 scope 找缺口時照該領域技能的方法做，產出照本節的規則處理；拆出的子項執行時也照該技能做。專業技能對不對，使用者無法從規格本身判斷，只能從結果驗收；agent 以驗收的回饋評估技能：翻案、重修、調整越少，技能越對，收尾檢討把驗收不通過的原因回寫到對應的技能（使用者 2026-10-24）。

### 子項類型

| 類型 | 綁定文件 | 誰驗收 |
|---|---|---|
| 直接工作 | 不建子項；commit 就是紀錄 | — |
| 直接執行的子項 | 不綁 checklist | 執行者對照標題與說明 |
| `self` | checklist，只有不標的檢查 | 執行者 |
| `manual` | 不標＋`[manual]` | 執行者、使用者 |
| `cross` | 不標＋`[acceptance]` | 執行者、另一個 agent |
| `cross manual` | 三種都有 | 執行者、另一個 agent、使用者 |
| 卡片結案驗收（新） | 只有 `[manual]` 的 checklist，對照卡片目標 | 使用者 |
| 決策 | `.decisions` | 使用者作答 |

- 直接工作與直接執行的子項都保留：沒有人會回頭看的用直接工作；使用者想在 Report 上追蹤的建子項。
- 「問題：」子項是評估的輸入，評估把它轉成修正、決策題或已排除方向。
- 中途要使用者確認的事分兩種：確認一個結果（「這個配色對嗎？確認後再套用到十頁」）用中途的 `[manual]`；確認一個選擇（「A 還是 B」）用決策題。

### 執行與驗收

- **方向錯就停。** 實作偏離規格，就地修正；規格或目標本身錯了，停下，不硬改到通過（[agent-work-route〈Separate a wrong implementation from a wrong spec〉](../../.agents/skills/agent-work-route/SKILL.md#separate-a-wrong-implementation-from-a-wrong-spec)）。目標錯回到〈釐清目標〉，規格錯重寫規格後繼續。
- **對照目標驗收。** 每一層驗收都判斷結果是否達成目標寫的意圖，不只對照步驟；條件本身不服務目標時，標「條件不符」。條件在執行前寫好並提交（〈已決定〉第 4 點）。
- **人工驗收不擋流程（第 4 題）。** 被等的子項只差使用者驗收時，等它的子項就解除等待；必須等使用者驗收的，宣告等待時標明「要等使用者驗收」。使用者之後驗收不通過，相依的子項跟著重做。

### 經驗紀錄

第 3 題。任務卡綁定一份 `experience/<卡片ID>.md`，和 checklist、決策檔並列，只裝執行中學到、之後可能改變做法的經驗。

- **綁定。** 卡片新增綁定文件的能力。不做 UI；這是給 agent 讀的文件，使用者要看就用文字編輯器。
- **格式。** 每筆一行：狀態、日期、寫入者、子項、類別、內容、影響的規則。

  ```markdown
  - [open] 2026-10-24 claude › derived-state-array-fallback › environment：Python 測試要加 PYTHONPATH=. 才跑得起來 → README〈測試〉
  - [promoted → TaskProgress/README.md#測試] …
  - [dismissed：只發生一次，不值得寫成規則] …
  ```

  類別：`misled`（某個步驟或規則誤導）、`missing`（缺一條規則或說明）、`environment`（工具或環境的坑）、`judgment`（沒有規則可依、當場做的判斷）。
- **不收什麼。** 進度、下一步、現況（屬於 Report 與 checklist）；要使用者選的事（決策檔）；要修的問題（「問題：」子項）。
- **指標行。** 收尾檢討在檔案末尾記一行成效指標（〈成效指標〉）。
- **處理。** 收尾檢討把每一筆 `open` 改成 `promoted`（附改到哪裡）或 `dismissed`（附理由），已處理的保留，供成效指標統計。卡片完成時不留 `open`。
- **handoff。** 只指路到卡片；範圍內的資訊（checklist、決策、經驗）都掛在卡片上。

### 量與分批

一個 session 能處理的量有限，對話越長品質越差。量太大時常見的失敗是為了完成而縮減：降低驗收標準、跳過步驟，最後回報完成。

- **不為了做完而縮減。** 做不完就停在完整的狀態（子項已建、決策已出、經驗已記），回報完成了哪些、剩下哪些；下一個 session 從 Report 接手，不從對話接手。
- **分批，越廣越淺。** 照優先順序一次處理一批，Report 本身就是佇列。全部自動跑完要靠多個 agent 平行（[WorktreeReportPlan](WorktreeReportPlan.md)），不由單一 session 硬撐。

### 收尾檢討

第 6 題。卡片最後一個工作子項完成後、交給使用者結案驗收之前，由完成它的 session 做一次：讀經驗紀錄並逐筆處理；比對結果與目標，還缺的補成子項或寫成決策題，不該再做的列為退場候選（[GapScanPlan](GapScanPlan.md)）；流程本身的問題寫成「問題：」子項；之後才把卡片結案驗收交給使用者，使用者驗收的是檢討、補齊之後的結果。收尾檢討是流程的一步，不是子項（[agent-executable-items〈What qualifies〉](../../.agents/skills/agent-executable-items/SKILL.md#what-qualifies)的收尾工作）。

### 輕量流程

第 5 題。依子項類型與直接工作，小任務本來就走輕的路徑，由 agent 依準則判斷，回報省略了哪些步驟與理由；使用者可以要求走完整流程。準則：指令已寫明可觀察的結果、只有一個步驟時，不另外釐清目標也不拆解；沒有經驗紀錄時，收尾檢討不做。

### 成效指標

| 指標 | 對應 | 現有資料 |
|---|---|---|
| 驗收不通過率（實作不符、條件不符） | 有效：任務更對齊 | checklist 的驗收結果 |
| 重做與重複說明次數（子項重開、使用者重講目標） | 有效、高效 | 子項重開有事件；重講目標沒有紀錄 |
| 週期時間（建立到完成） | 高效 | Report 事件的時間 |

第 7 題。收尾檢討時算出這張卡的數字，在經驗紀錄檔末尾記一行，例如 `指標：驗收不通過 1／5、重做 0、重講目標 1、週期 3 天`；不寫程式，要彙整時用 `grep`。數字證明有用後，再考慮搬進 Viewer 的時間分析。重講目標沒有現成紀錄，由收尾檢討從經驗紀錄與對話回顧計數。

- **agent-executable-items〈Evaluate a scope〉：** 從目標推得出的工作直接建立；評估改讀卡片的經驗紀錄，不再讀 friction log。

## 已決定

使用者於 2026-10-21、22 決定：

1. 只有「驗收通過」才算完成；Report 要分得出執行者做完、等待驗收、驗收不通過。
2. 檢查標籤是權限標籤，只接受程式登記過的標籤：不標（執行者）、`[manual]`（使用者）、`[acceptance]`（執行者以外的 agent）。
3. 一個可執行項目只綁一份 checklist，執行、他驗、人工檢查都在同一份。
4. `[acceptance]` 的檢查條件在規劃時寫好並先提交，才開始執行；條件從原始需求推導，每個 `[acceptance]` 檢查寫明它對照的規格出處。寫條件的人可以就是執行者（AC-07）：要防的是「看過實作才寫條件」，這由順序、提交與改動檢查擋住，不靠換人；建立者自己誤解需求的風險，則靠驗收者回頭對照原始需求，所以建立者不能驗收。
5. 「執行者以外」指獨立驗收上下文（見〈獨立驗收上下文〉）：驗收者不繼承執行者的對話歷史與推理。`session_id` 只是記錄身分、讓 CLI 擋下執行者的識別方式，不是獨立判斷的證明；執行者留在原上下文切換角色，或只更換 session ID，都不算。
6. `[acceptance]` 主要由 agent 記錄。使用者可以在面板改它的結果，改之前跳出確認「確認修改 agent 紀錄嗎？」。
7. 每個 `[acceptance]` 與 `[manual]` 結果都記下記錄者（agent 的 session，或 `user`）與記錄當下該檢查內容的指紋。沒有記錄者的結果不算數；內容改過、指紋對不上時，結果自動失效，顯示「需重驗」。
8. `[manual]` 檢查在規劃時就寫好初稿；執行與驗收之後，執行者與驗收者可以補上或調整得更明確。它的目的始終是「使用者能不能接受這件事完成」。
9. 執行者與驗收者不能把 `[manual]` 標成 `[x]`，只能標 `[!]`，意思是「需要使用者再驗一次」，並在 `Observed` 寫明原因。只有使用者能標 `[x]`。
10. 入口是一個 Claude skill，斜線命令 `/task-progress-items`（見〈命令〉）。其他工具的對齊由使用者另外處理。
11. 沒有指定驗證方式時，由 agent 依〈驗證方式的判斷依據〉替每一項選擇，並在回報中寫出每一項的選擇與理由。使用者想強制時，在指示前加 `self`、`manual`、`cross` 或 `cross manual`。
12. 驗證流程只在觸發時使用，不依項目內容自動套用。現行「改動規格或程式碼時，另一個 agent 審查並寫在 handoff」的規則刪除，需要獨立驗收時改用 `[acceptance]`。
13. 只有他驗需要獨立驗收上下文，而且只要求驗收者不是建立者或執行者。自驗與人工可以在同一個 session 規劃並執行，與過去相同。
14. 一次處理多個項目時，能開子 session 就每項開一個；同一個 scope 一次一個，前一個通知完成才開下一個；不同 scope 可以同時。
15. `run`、`accept` 不帶代號時處理全部可處理的項目；帶卡片代號只處理那張卡，帶項目代號只處理那一項。
16. 綁定 checklist 的子項，狀態一律從 checklist 推算；存起來的只有「誰認領了」。重驗出問題時，子項自動重新顯示為未完成。
17. 標籤檢查的先後由程式判斷，不在 checklist 裡寫依賴清單：`[acceptance]` 等所有不標的工作項目完成；`[manual]` 再等所有 `[acceptance]` 通過，避免他驗不過、實作改了之後使用者白驗一次。
18. `/task-progress-items <指示>` 建立項目後直接執行；他驗項目執行完，交給獨立驗收上下文驗收。
19. 計畫保留〈流程紀錄〉，同一組情境寫兩份：〈使用者流程〉給使用者看（命令、Report 上看到什麼、輪到誰），〈Agent 流程〉給 agent 看（依哪條規則、認領與事件）。改規則時兩份都重走。
20. 子項可以宣告它在等哪些子項（可跨 scope），推算出「等待中」；被等的全部完成後自動解除，不需要手動設受阻（AC-08）。收合時子項仍是一行，只多「等待中」標籤；展開後列出每個被等子項的連結（見〈等待〉）。
21. 既有 checklist 一次遷移（AC-09）：替所有已登記 scope 中，已有結果卻沒有記錄者的標籤檢查補上記錄者 `legacy` 與內容指紋。遷移工具保留為命令，之後發現漏掉的舊檔也用它轉換。程式不在讀取時自動轉換，因為分不出「新規則前的舊結果」與「新規則後直接改檔案打的勾」。
22. 沒有記錄者的標籤結果：`checklist validate` 失敗並說明處理方式；面板與 Report 照常開啟，只把那幾個結果顯示為「需重驗」並註明原因，子項依此推算為未完成。
23. 驗收者發現條件本身與原始規格對不上時，標 `[!]` 並選原因「條件不符」，交給建立者修改條件；建立者改完，由驗收者對照規格確認。建立者不同意，或驗收者不接受修改，才交給使用者決定（見〈條件不符〉）。
24. `[acceptance]` 是執行者以外的獨立判斷，不是共識：判斷實作是否符合時，驗收者單獨決定，執行者沒有表決權；只有條件本身被質疑時，才需要建立者與驗收者取得共識，談不攏由使用者裁決。
25. 一個子項只綁一份 checklist；其他相關的 checklist 以連結寫在子項描述裡，不綁定。
27. 不帶參數的 `/task-progress-items` 等同 `auto`；只評估不執行改為 `plan` 動詞；帶卡片或項目代號也等同 `auto <代號>`，`plan <代號>` 只評估那張卡或回報那一項的狀態（使用者 2026-10-23，[agent-workflow.decisions](../decisions/agent-workflow.decisions) 第 1 題）。
28. 評估產生的決策題，屬低風險（可逆、不改已發布規格或設計資料、不跨 scope、不屬產品偏好）時由 agent 直接採建議作答並執行，答案的 reason 記「採建議，未經使用者確認」，回報列出；其餘等使用者。評估先讀已答但未落實的決策（第 2 題）。
29. agent 執行、分析、評估中發現且不在本項目範圍內的問題，記為擁有卡上標題前綴「問題：」的子項（優先級 2、不綁 checklist、經 report CLI 新增）；找不到擁有 scope 的進 `.agents` 的 known-issues 卡。覆盤就是對那張卡執行評估，把「問題：」項目分到修正項目、決策題或 ruled out（第 4 題）。
26. 對每個 agent，明確呼叫 `task-progress-items`（Claude 為 `/task-progress-items`）是啟動可執行項目流程的唯一入口（見〈入口邊界〉；2026-10-22 起其他 agent 也對齊，經各自的使用者層入口）。一般開發要求、「請繼續發展任務」等舊短語、單獨提供項目 ID，以及專案有 `checklists/`，都不構成啟動條件；讀取 checklist 或 Report 的格式與權限規則，也不等於啟動流程。

## 一份 checklist 的樣子

```markdown
- [ ] **1. 數值欄位支援小數位**
  Outcome: 設定欄位依規格顯示與提交小數。
  Checks:
    - [ ] **單元測試**
      - Action: 執行 numeric-field 測試。
      - Expect: 全部通過。

- [ ] **2. 他驗**
  Outcome: 執行者以外的 agent 依原始需求確認結果。
  Checks:
    - [ ] **驗收條件未被改動** `[acceptance]`
      - Action: 以 git 檢查本檔第 2 項自建立者提交後的變更。
      - Expect: 只有標記與記錄者變動。
    - [ ] **小數位與規格一致** `[acceptance]`
      - Action: 對照規格的小數位表，審查 `git log --grep <子項 ID>` 列出的變更。
      - Expect: 每一列都有對應實作與測試。

- [ ] **3. 人工驗收**
  Outcome: 使用者接受這項修改。
  Checks:
    - [ ] **設定分頁的小數輸入** `[manual]`
      - Action: 開啟 [Apps 設定分頁](http://127.0.0.1:8015/demo/apps/)，輸入 1.25 並離開欄位。
      - Expect: 顯示 1.25，越界時有提示。
      - Reason: 操作感受由使用者判。
```

第 2、3 項不寫 `Depends on`：程式自動讓第 2 項等第 1 項這類不標的工作項目全部完成，第 3 項再等第 2 項全部通過（已決定第 17 點）。記錄者與內容指紋的欄位名稱、位置與指紋算法在實作時決定。

## 命令

scope 預設是目前所在的專案，只有需要時才另外指定。

```text
/task-progress-items                  等同 auto：評估、做掉直接做的工作、執行、驗收
/task-progress-items plan [卡片或項目]   只評估：建立項目並列出直接做的工作，不執行；卡片只評估這張卡；項目回報它的狀態與下一步命令
/task-progress-items plan all            對每個已註冊 scope 依序做 plan，各自設定 Next，最後彙整成一份報告；只有 plan 能用 all（使用者 2026-10-23）
/task-progress-items <卡片或項目>       等同 auto <卡片或項目>
/task-progress-items <指示>            把使用者說的一件事寫成項目，接著直接執行
/task-progress-items run [卡片或項目]    執行
/task-progress-items accept [卡片或項目] 驗收
/task-progress-items auto [卡片或項目]   評估、做掉直接做的工作、執行、驗收；卡片只做這張卡，項目略過評估
```

- **直接做的工作**：評估發現的工作，只有之後有人或流程要讀回紀錄時才建成項目，例如需要他驗或人工驗收、有項目要等它、要交給另一個 session，或使用者要在 Report 上追蹤。機械性、看提交就能確認、沒人要追蹤的工作（搬移或改名檔案、修正連結）不建項目也不寫 checklist；一般評估只列出，每項附一句可以直接交代給 agent 的話；`auto` 由評估的 session 先做掉、逐項提交，在回報中列出，不寫進 Report（2026-10-22）。
- **未綁定的既有項目**：卡片上沒綁 checklist 的子項（使用者手動追蹤的項目）也可以執行，沒有驗證階段。`run`／`auto` 依推算狀態與相同順序挑它，`accept` 不挑；執行時認領、做事、照標題與描述自行檢查、提交訊息帶項目代號，最後以 `item.update` 設為 `done`，不釋放（釋放會改回 `planned`，項目會回到佇列）。評估把它當成既有工作，不重複建立（2026-10-22）。

- 「卡片或項目」可以是代號、從 Viewer 複製的項目參照，或完全相同的卡名／項目名（不分大小寫）。只部分符合某個名稱，或同名不只一個時，列出候選與代號後停下，不建立任何項目，避免打錯的卡名變成新項目（2026-10-22）。

- 「指示」是一句描述具體工作的話，例如「修正 NumericField 越界時沒有提示」。agent 判斷它屬於哪張卡，新增項目、寫好 checklist 並提交，然後在同一個 session 執行。驗證方式含他驗時，執行完交給獨立驗收上下文：能開不繼承上下文的子 agent 就由它執行 `accept <項目代號>`，否則告訴使用者在新的 chat 執行。
- 在指示前加 `self`、`manual`、`cross` 或 `cross manual` 可以強制驗證方式，例如 `/task-progress-items cross 修正 X`。平常不加。
- 評估的回報要列出每一項選了哪種驗證方式與理由。

### 入口邊界

- 對每個 agent，只有明確呼叫 `task-progress-items` 會建立項目、認領、執行或啟動驗收。
- 使用者用了舊短語（「請繼續發展任務」「請評估 <scope> 並建立可執行項目」「請執行 <scope> report 的可執行項目」等）時，agent 不啟動流程，回一句對應的命令，例如「要評估並建立項目，請用 `/task-progress-items`」，讓使用者知道沒有被忽略。
- 一般開發要求照一般方式處理，不因專案有 `checklists/` 就建立 checklist 或項目。
- 直接操作既有 checklist 或 Report（例如調整某份 checklist 的步驟）時，照該文件的格式、寫入權限與驗證規則處理；載入這些規則不授權建立項目、執行工作或啟動驗收。
- 共用索引 `.agents/AgentsKnowledgeIndex.md` 只有一列路由可執行項目：所有 agent 先經 taskprogress-capabilities 確認使用者層入口，再由入口讀共用的 task-progress-items；舊短語不啟動任何 agent 的流程。`agent-executable-items` 只留項目的判斷準則（位置、評估、資格、形狀），不再是流程入口（2026-10-22）。
- 生效時機：skill 完成（實作項目第 6 項）時才一起改索引與舊 skill；在那之前現有入口照常可用，避免中間有一段時間叫不動任何流程。

### 驗證方式

| 方式 | checklist 內容 | 需要的 session |
|---|---|---|
| `self` 自驗 | 只有不標的檢查 | 1 |
| `manual` 人工 | 不標＋`[manual]` | 1，另加使用者 |
| `cross` 他驗 | 不標＋`[acceptance]` | 2：執行（可兼規劃）、驗收 |
| `cross manual` 他驗＋人工 | 三種都有 | 2，另加使用者 |

### 驗證方式的判斷依據

沒有指定時，agent 依下列依據替每一項選擇：

- 結果有只有使用者能判斷的部分（外觀、操作感受、要在使用者裝置上確認）→ 加人工。
- 需求容易被理解錯：要從規格推導實作，或改動已發布的規格、設計資料、案例、程式碼 → 加他驗。
- 其他 → 自驗。

### `run` 與 `accept` 處理哪些項目

依〈子項狀態〉推算出的狀態挑選，只看綁定 checklist 的子項：

- `run`：未開始、執行中且沒有別人認領、需修正且沒有人認領的項目，以及條件待修的項目（跳過自己是提出問題的驗收者的）。等待中的不挑。
- `accept`：待他驗的項目，跳過這個 session 建立或執行過的項目。
- 執行者自己的 `[!]`（環境或規格問題）讓子項停在待使用者，`run` 不會自動挑。使用者處理完、以 `run <項目代號>` 指名時才重跑那一項（checklist-round 現行規則：介入完成後重跑一次）。
- 順序：優先級高的先做，同優先級依卡片在 Report 中的順序。一項做完並提交後才做下一項。

### 一次處理多個項目

| 情況 | 做法 |
|---|---|
| 指定一個項目代號 | 在目前的 session 直接做；`accept` 而這個 session 建立或執行過該項時，改由獨立驗收上下文驗收（不繼承上下文的子 agent，不能開時請使用者開新的 chat） |
| 多個項目，能開子 session | 每項開一個子 session；同一個 scope 一次一個，收到前一個完成的通知才開下一個；不同 scope 可以同時 |
| 多個項目，不能開子 session，`run`／`accept` | 做完一項就停，列出下一個候補，等使用者說繼續 |
| 多個項目，不能開子 session，`auto` | 全部自己執行；他驗項目的驗收交給獨立驗收上下文：能開不繼承上下文的子 agent 就由它驗收，否則列出來，請使用者在新的 chat 執行 `accept` |

同一個 scope 不同時開多個子 session，是因為每一項都會改同一份 `report.json`、handoff 與程式碼，同時寫會互相覆蓋或混進對方的提交；各自開工作目錄（worktree）則本機服務看不到進度，合併時 `report.json` 也幾乎必定衝突。子 session 由父 session 依序開啟、收集結果，最後給使用者一份簡短回報。驗收也寫同一個 scope，所以一項的驗收完成後才開下一個子 session。有些宿主開子 session 需要使用者在畫面上確認一次。

## 規則

### 角色

| 角色 | 怎麼認定 |
|---|---|
| 建立者 | 建立子項、寫 checklist 與 `[acceptance]` 條件的 session；條件被標「條件不符」時負責修改。原 session 已結束時，由提出問題的驗收者以外的任何 session 代為修改，代為修改的 session 也算建立者。評估專案、替項目寫條件的 session 就是建立者，沒有另外的「規劃者」角色 |
| 執行者 | 每一個開始或接手過這個子項的 session（`started`、`takeover`），不只最後一個；可以就是建立者 |
| 驗收者 | 記錄 `[acceptance]` 結果的獨立驗收上下文（見下一節），不得是建立者或任何一個執行者；判斷實作時單獨決定，條件被質疑時與建立者取得共識 |
| 使用者 | 唯一能把 `[manual]` 標成 `[x]` 的人；條件爭議的最後裁決者 |

他驗流程的每一次寫入（Report 與 checklist）都必須帶 `session_id`，缺少時拒絕；沒有內建 session ID 的工具，在 session 開始時自己產生一個並全程沿用。子 agent 使用自己的穩定 ID，不借用或改換執行者的。

### 獨立驗收上下文

`[acceptance]` 由沒有建立該項目、也沒有實作或修正它的獨立驗收上下文執行，避免執行者自問自答、沿用自己的錯誤假設，或為了讓結果通過而降低標準。驗收者：

- 從原始需求、已提交的驗收條件、產物與變更紀錄獨立判斷。
- 不繼承執行者的對話歷史、推理過程或預期結論。
- 可以取得必要的執行事實、測試證據與操作方式。
- 不接受要它通過的暗示，也不為配合實作而降低標準。
- 有權判定實作不符或條件不符，記錄依據並要求修正。

新的 chat、獨立的 session，或不繼承父上下文的子 agent，都可以擔任驗收者。由執行者開啟的子 agent，交代的只有子項代號與驗收命令，不附工作摘要或預期結果。執行者留在原上下文自行切換角色，或只更換 session ID，不符合獨立驗收。

驗收者可以保留自己的驗收歷史，持續追蹤同一項目的修正與重驗，不必每次重驗都建立新上下文。

`session_id` 與上下文是兩件事：`session_id` 記錄是誰、讓 CLI 拒絕執行者的結果；上下文是否獨立，CLI 無從驗證，由 agent 遵守（〈已知限制〉）。

### 認領

- 存起來的只有認領：開始或接手時記 `started`／`takeover`，做完或修完時以 `item.event` 記 `released`（新事件），同時把存起來的狀態從 `in_progress` 改回 `planned`，下一個接手的 session 才會重新記到 `started`。最後一筆開始或接手之後沒有 `released`，就是被那個 session 認領中。
- 認領的衝突判斷沿用 ItemActivityLog 現行規則，`released` 也照它判定：只能釋放自己的認領。
- 執行者的釋放與工作放在同一個提交：驗證 checklist、記 `released`，再把工作與 `report.json` 一起提交。中斷時兩者一起留在未提交的變更裡，不會出現「已提交、未釋放」或「已釋放、未提交」只剩一半的狀態。
- 恢復：認領者的 session 已結束，`git log --grep <子項 ID>` 顯示它的工作已提交（修正時，提交晚於那筆失敗結果的記錄時間），相關路徑沒有未提交的變更，只差釋放時，其他 session 向使用者說明，經同意後以 `claim: "recover"` 代為釋放。代為釋放不記 `takeover`，不算執行者。工作沒做完的照〈例外情況〉的接手處理，不用恢復。
- 活動紀錄保留規則：`created` 與每一筆 `started`、`takeover` 永久保留；`released`、`disputed` 各保留最近一筆；其他事件只留最近 3 筆。

### 子項狀態（推算）

綁定 checklist 的子項，Viewer、`report get`、時間分析與佇列都用下面的推算結果，不讀存起來的 `status`。依序判斷，第一個成立的就是它的狀態：

| 狀態 | 條件 |
|---|---|
| 完成 | 每一項檢查都是 `[x]`，且標籤檢查都有記錄者、指紋都對得上、記錄時間不早於最近一次 `released` |
| 等待中 | 宣告等待的子項中，有任何一個還沒完成（見〈等待〉） |
| 待使用者（爭議） | 「條件不符」的 `[acceptance]` 進入爭議（見〈條件不符〉） |
| 條件待修 | 有原因為「條件不符」的 `[acceptance]` `[!]`，條件還沒修改 |
| 需修正 | 有原因為「實作不符」的 `[acceptance]` `[!]` 或使用者記的 `[manual]` `[!]`，且該結果在 `Recorded` 裡的時間晚於最近一次 `released`（還沒修好） |
| 待使用者 | 有執行者自己的 `[!]`（環境或規格問題）、agent 記的 `[manual]` `[!]`，或其餘都完成而 `[manual]` 尚未完成（含「需重驗」的 `[manual]`） |
| 待他驗 | 不標的工作項目全部 `[x]`，`[acceptance]` 未完成（含修好後等重驗，以及「需重驗」的 `[acceptance]`） |
| 執行中 | 有人認領，或曾經開始過 |
| 未開始 | 以上皆非 |

因為 `[manual]` 要等 `[acceptance]` 全部通過，待他驗與待使用者的人工驗收不會同時出現：`[acceptance]` 與 `[manual]` 同時需重驗時，先待他驗。

### 等待

- 子項新增欄位，列出它在等的子項，每一筆以 scope、卡片、子項代號指定，可以跨 scope。schema 的子項目前不接受額外欄位，需要一併新增；由 Report CLI 寫入。
- 被等的子項是否完成，用它自己的推算狀態判斷；沒有綁定 checklist 的子項，照現行做法看它存起來的狀態。跨 scope 時讀取該 scope 登記的 Report 與 checklist。被等的子項不存在或讀不到時，視為未完成，並在畫面上標出無法讀取。
- 互相等待（A 等 B、B 等 A，或更長的環）會讓雙方永遠等待中：`report validate` 與 Report CLI 寫入時拒絕形成環的宣告。
- 子項在等待中時，`run` 不挑它；全部完成後自動回到原本推算的狀態。
- 畫面：收合時子項維持一行，只在右側多一個「等待中」標籤。展開（「…更多」）後，完整標題後面列出「等待：」與還沒完成的被等子項所在的卡片，每張卡一個連結，文字為卡片標題，後面標「（N 項未完成）」，點下去開啟對方卡片並置頂。連結只能定位到卡片，同一張卡逐項各列一個連結點下去都一樣；是哪幾項未完成，在對方卡片上看得到。依賴本身仍逐項記錄與判斷，被等子項分在不同卡片時各卡各一個連結。已完成的不計入，整張卡都完成就不再列出；讀不到的被等子項單獨以「卡片 › 子項（無法讀取）」列出。沿用現有的行內連結與描述展開元件；卡片第一個未完成子項本來就預設展開，因此不必點也看得到。
- 「等待中」標籤本身可按（使用者 2026-10-23）：只等一張卡或一份 checklist 時，標籤就是連到它的連結；等多個對象時，按下展開一份清單，每張卡或每份 checklist 一個連結，讀不到的列名稱不給連結，焦點離開或按 Esc 收起；全部讀不到時標籤不可按。編輯模式不提供。實作在 `item-state.js` 的 `waitLinks` 與 `ItemRow.svelte`，測試 `tests/waiting-capsule.test.mjs`。
- 不用 tooltip 放連結：滑鼠移開就消失，觸控與鍵盤也無法操作。

### 條件不符

驗收者對照原始規格，發現 `[acceptance]` 條件本身寫錯時：

1. 驗收者標 `[!]`，原因選「條件不符」，`Observed` 寫明對照的規格段落與哪裡對不上。推算：條件待修（不是實作的錯，不算需修正）。
2. `run` 挑到它，由建立者（或提出問題的驗收者以外的 session）處理：
   - 同意：修改條件並提交，提交訊息帶子項 ID 並註明「條件修訂」；這次提交成為「驗收條件未被改動」的新比對基準。條件內容改了，驗收者原本的 `[!]` 因指紋對不上而失效 → 推算：待他驗。
   - 不同意：在子項記一筆 `disputed`（新事件），寫明理由 → 推算：待使用者（爭議）。
3. `accept` 挑到它，驗收者對照規格確認修改後的條件：
   - 接受：照新條件驗收實作；實作跟不上新條件時，記「實作不符」交回執行者。
   - 不接受：同一項檢查第二次標「條件不符」→ 直接推算為待使用者（爭議），不再來回。
4. 使用者裁決：說明正確的條件，由 agent 照著修改；或在面板直接改那一項的結果（照已決定第 6 點先確認）。
5. 驗收者不能自己改條件再自己確認。

原因與第幾次標記，記在 `[acceptance]` 結果的記錄者欄位旁，欄位格式實作時決定。

### 寫入與記錄者

- 不標的檢查照現行做法，由執行者直接編輯檔案記錄。
- `[acceptance]` 與 `[manual]` 的結果只經 CLI（`checklist request`，帶 actor 與 session）或面板寫入，寫入時記下記錄者與該檢查 `Action`、`Expect` 的內容指紋。權限：
  - `[acceptance]`：session 與建立者（`created`）或任一執行者相同時拒絕；寫 `[!]` 必須選原因「實作不符」或「條件不符」；使用者經面板寫入時先確認。
  - `[manual]`：agent 只能寫 `[!]`，且必須附 `Observed`。
- 結果的記錄時間寫在 checklist 的 `Recorded` 裡，推算拿它和最近一次 `released` 比較，判斷修好了沒有；checklist 的寫入不碰 Report（實作時以此取代原本規劃的 `rejected` 事件）。
- 先後（已決定第 17 點）：不標的工作項目還沒全部 `[x]` 時，拒絕寫入 `[acceptance]`；`[acceptance]` 還沒全部通過時，拒絕寫入 `[manual]`。
- checklist 沒有綁定子項時，agent 的標籤寫入一律拒絕（無法判斷執行者）；使用者經面板仍可寫，讓舊的一頁一份人工 checklist 照常可用。
- 有 `[x]`／`[!]` 卻沒有記錄者的標籤檢查：`checklist validate` 失敗，指出行號並提示「新規則前的舊結果請執行遷移命令，否則重新記錄」；面板與 Report 照常開啟，該結果顯示為「需重驗」並註明沒有記錄者。這擋的是執行者直接改檔案替它打勾。
- 讀取時重算指紋；內容改過的結果自動失效為「需重驗」，不論是經命令還是直接改檔案改的。
- 重新執行後的結果失效：標籤檢查的 `[x]`，記錄時間早於子項最近一次 `released` 時，失效為「需重驗（之後重新執行過）」。釋放代表執行者交出了新的工作，之前的通過不再證明現在的實作，包括修正一項失敗時順帶改到的其他部分。`[!]` 不受影響，釋放正是用來表示它已修好（〈子項狀態（推算）〉的需修正）。checklist 本身不知道 Report，推算、面板與 `checklist request` 都從綁定的子項讀最近一次 `released` 再判定；先後規則也用失效後的結果，所以 `[manual]` 會再次鎖住，等 `[acceptance]` 重驗。
- 遷移命令（名稱實作時定）替指定檔案中沒有記錄者的標籤結果補上記錄者 `legacy` 與指紋。只由人或 agent 明確執行，程式不在讀取時自動轉換。

### 內容凍結

- 不標的檢查與 `[acceptance]`：記過結果後凍結標題、`Action`、`Expect`（現行規則）。唯一例外是〈條件不符〉的條件修訂。
- `[manual]`：可以隨時修改或新增（已決定第 8 點）；改過的結果因指紋失效而需重驗。

### 交接

- 含 `[acceptance]` 的 checklist 與綁定先提交，才開始執行，即使執行的是同一個 session；這個提交是「驗收條件未被改動」的比對基準。
- 他驗項目的執行者，每個提交訊息都帶子項 ID，驗收者以 `git log --grep <子項 ID>` 找出變更。
- 他驗工作項目的第一個檢查固定是「驗收條件未被改動」：以 git 確認 `[acceptance]` 的內容自那次提交（或最近一次「條件修訂」提交）後沒有被改。
- 每個 `[acceptance]` 檢查的 `Action` 寫明對照的規格出處，驗收者據此回頭看原始需求，而不只看 checklist 的寫法。

## 流程紀錄

同一組情境寫兩份，編號互相對應：〈使用者流程〉給使用者看，寫命令、Report 上看到什麼、輪到誰；〈Agent 流程〉給 agent 看，寫每一步依哪條規則、認領與事件怎麼變。改規則時兩份都要重走一遍，確認每一步都有規則可依、沒有兩條規則衝突。`/task-progress-items` skill 實作後，Agent 流程的操作步驟由 skill 擁有，這裡只留情境與對應規則。

### 使用者流程

共同的開頭：App 啟動、Report 開啟時，每個綁定 checklist 的子項讀取它的 checklist，推算出狀態與是否完成。

#### 1. 自驗

1. 你：`/task-progress-items 修正 X`。
2. Agent 分析任務，在對應的卡片建立子項，綁定一份 checklist（只有自驗檢查），接著執行並自驗。
3. Report：子項顯示「執行中」，自驗全部通過後顯示「完成」。

#### 2. 人工

1. 你：`/task-progress-items 修正 X`，agent 評估需要人工驗收（或你加了 `manual`）。
2. Agent 建立子項，checklist 含自驗檢查與 `[manual]` 初稿；執行、自驗，並補上 `[manual]` 的連結。
3. Report：子項顯示「待使用者」。
4. 你：開啟子項的 checklist，照連結逐項驗收。
   - 全部通過 → Report 顯示「完成」。
   - 標了 `[!]` → 顯示「需修正」；agent 以 `run` 修正後回到「待使用者」，你重驗，先前通過的項目也要再確認一次。

#### 3. 他驗

1. 你：`/task-progress-items 修正 X`，agent 評估需要他驗（或你加了 `cross`）。
2. Agent A 建立子項，checklist 含自驗檢查與寫明規格出處的 `[acceptance]` 條件，先提交，再執行、自驗。
3. Report：子項顯示「待他驗」。A 能開不繼承上下文的子 agent 時交給它驗收；不能時提示你開新的 chat 驗收。
4. 你（需要時）：在新的 chat 執行 `/task-progress-items accept`。
5. Agent B 對照規格驗收：
   - 通過 → Report 顯示「完成」。
   - 實作不符 → 顯示「需修正」；`run` 修正後回到「待他驗」，B 重驗，包括先前通過的項目。
   - 條件不符 → 見情境 5。

#### 4. 他驗＋人工

1. 同情境 3 的第 1～5 步，只是 checklist 另有 `[manual]`。
2. 他驗全部通過前，`[manual]` 鎖住，Report 顯示「待他驗」；你不會在這時被叫來驗。
3. 他驗通過 → Report 顯示「待使用者」，你照情境 2 的第 4 步驗收。

#### 5. 條件不符

1. 驗收者 B 發現 `[acceptance]` 條件與規格對不上，標「條件不符」並寫明哪一段。Report 顯示「條件待修」。
2. 建立者（或 B 以外的 session）以 `run` 處理：
   - 同意 → 修改條件並提交，Report 回到「待他驗」，B 確認新條件後照它驗收。
   - 不同意 → Report 顯示「待使用者（爭議）」，輪到你。
3. B 不接受修改後的條件 → 同樣顯示「待使用者（爭議）」。
4. 你裁決正確的條件，agent 照著修改；或在面板直接改那一項的結果。

#### 6. 評估整個專案

1. 你：`/task-progress-items plan`。Agent 評估，建立多個子項，回報每一項選了哪種驗證方式與理由；不執行。低風險的決策題 agent 已採建議作答並在回報列出，你不同意就在決策頁改答案。
2. 你：`/task-progress-items run`。能開子 session 時，每項一個子 session，依序執行；不能開時做完一項就停，列出下一個候補。
3. 有他驗的項目：Report 顯示「待他驗」，由獨立驗收上下文執行 `accept`；agent 不能開不繼承上下文的子 agent 時，你在新的 chat 執行。
4. `/task-progress-items auto`（不帶參數時的預設）等於第 1、2 步連續做完；原本的 session 建立了這些項目，所以不自己驗收，他驗交給不繼承上下文的子 agent，不能開時留給你在新的 chat 執行。

#### 7. 等待

1. 子項 U 宣告在等其他卡片（可跨專案）的 W1、W2。
2. Report：U 收合時顯示「等待中」；展開後列出 W1、W2 的連結，點下去開啟對方卡片並置頂。`run` 不挑 U。
3. W1 完成 → 只剩 W2 的連結；W2 也完成 → U 自動回到原本的狀態，可以執行。

#### 8. 例外情況

- 執行到一半停住，經你同意由另一個 session 接手：兩個 session 都算執行者，都不能驗收。
- 執行者已提交工作、還沒釋放就中斷：另一個 session 確認工作確實已提交後問你，你同意才代為釋放；代為釋放的 session 不算執行者。
- 完成後又有人重新執行並釋放：先前的驗收結果都顯示「需重驗（之後重新執行過）」，子項回到「待他驗」或「待使用者」。
- 執行中途多了一個自驗工作項目：`[acceptance]` 自動等它完成。
- 完成後有人改了 `[manual]` 的內容：那一項顯示「需重驗」，子項回到「待使用者」。
- 漏遷移的舊檔：`checklist validate` 失敗並提示遷移；面板照常開啟，該項顯示「需重驗（沒有記錄者）」。確認是舊結果就執行遷移命令；若是 agent 直接打的勾，由你重新驗收。

### Agent 流程

A、B、C 代表不同的 session；「推算」指〈子項狀態（推算）〉的結果。

#### 1. 自驗

1. A 建立子項，寫 checklist（只有不標的檢查）並綁定。
2. A 認領（`started` A），執行，在檔案裡勾 `[x]`，釋放（`released`），連同 `report.json` 一起提交。推算：完成。

#### 2. 人工

1. A 建立子項，checklist 含不標的檢查與 `[manual]` 初稿；綁定、認領、執行、勾 `[x]`，補上 `[manual]` 的連結，釋放並提交。推算：待使用者。
2. 使用者在面板記 `[manual]`（記錄者 `user`）。全部 `[x]` → 完成。
3. 使用者記 `[!]` → 推算：需修正。`run` 挑到它：A（或任何 session）認領、修正、釋放並提交 → `released` 晚於那筆 `[!]` 的記錄時間 → 推算：待使用者，等使用者重驗；先前通過的 `[manual]` 也因早於這次釋放而需重驗。

#### 3. 他驗

1. A 建立子項，寫 checklist（不標的檢查，以及寫明規格出處的 `[acceptance]`）並綁定，先提交。
2. A 認領、執行、釋放，提交訊息帶子項 ID。推算：待他驗。A 開不繼承上下文的子 agent B 驗收，只交代子項代號與 `accept`；不能開時，提示使用者在新的 chat 執行 `accept`。
3. B `accept`：B 不是執行者，也沒有 A 的對話歷史。第一項以 git 確認條件自 A 的提交後未改；其餘對照規格。
   - 全部通過：經 CLI 記 `[x]`（記錄者 B）→ 完成。
   - 實作不符：記 `[!]`、原因「實作不符」→ 推算：需修正。A `run` 認領、修正、釋放並提交 → 推算：待他驗；B 重跑失敗的檢查，通過時改 `[x]` 並加 `Resolved`，先前通過、早於這次釋放而需重驗的檢查也重跑一次。
   - B 若自己動手修正，就成了執行者，須由 C 驗收。

#### 4. 他驗＋人工

1. 同 Agent 流程 3；checklist 另有 `[manual]` 初稿。
2. `[acceptance]` 全部通過前，CLI 與面板拒絕寫入 `[manual]`。推算：待他驗。
3. `[acceptance]` 全部通過 → 推算：待使用者 → 照 Agent 流程 2 的第 2、3 步。使用者記 `[!]` 後的修正釋放，同時讓已通過的 `[acceptance]` 需重驗 → 推算：待他驗，他驗通過後才回到待使用者。

#### 5. 條件不符

1. B 記 `[!]`、原因「條件不符」，`Observed` 寫明規格段落。推算：條件待修。
2. `run` 由 B 以外的 session（建立者 A 優先）處理：
   - 同意：修改條件，提交訊息帶子項 ID 並註明「條件修訂」（成為新的比對基準）。B 原本的 `[!]` 指紋對不上而失效 → 推算：待他驗。
   - 不同意：記 `disputed` → 推算：待使用者（爭議）。
3. B `accept`：確認新條件後照它驗收；不接受則同一項第二次記「條件不符」→ 推算：待使用者（爭議）。
4. 使用者裁決後，agent 照指示修改條件，或使用者在面板改結果。

#### 6. 評估整個專案

1. P `plan`：先讀已答但未落實的決策並落實；評估，低風險決策題採建議作答（reason「採建議，未經使用者確認」）；建立子項並逐項選驗證方式，綁定、提交；回報選擇、理由與代答的題，不執行。
2. `run`：能開子 session 時，P 依序為每項開子 session C1、C2……，同一 scope 一次一個；子 session 認領、執行、釋放後通知 P。不能開時，P 做完一項就停，列出下一個候補。
3. `auto`：同上連續做完。P 是建立者，不驗收：他驗項目交給不繼承上下文的子 agent 驗收，驗收完才開下一個子 session。不能開子 session 時，P 自己執行全部項目，驗收同樣交給子 agent；也不能開子 agent 時，列給使用者在新的 chat 執行。

#### 7. 等待

1. U 經 Report CLI 宣告等待 W1、W2（寫入時檢查不形成環）。
2. 推算時讀取 W1、W2 的推算狀態（跨 scope 讀取該 scope 的 Report 與 checklist）；任一未完成 → U 為等待中，`run` 不挑。
3. W1、W2 都完成 → U 回到原本推算的狀態。

#### 8. 例外情況

- B 執行到一半停住，經使用者同意 C 以 `takeover` 接手：B、C 都是執行者，都不能驗收。
- B 已提交工作、還沒釋放就結束：C 依〈認領〉的恢復條件確認後問使用者，同意後以 `claim: "recover"` 代為釋放。C 不是執行者，之後仍可驗收。
- 完成後又有 session 認領、修改並釋放：先前的標籤通過結果都早於這次釋放而需重驗 → 推算回到待他驗（有 `[acceptance]` 時）或待使用者。
- 執行中途新增不標的工作項目：`[acceptance]` 自動等它完成，不改依賴。
- 完成後 `[manual]` 內容被改：指紋失效，推算回到待使用者。
- 漏遷移的舊檔：`checklist validate` 失敗並提示遷移命令；推算把沒有記錄者的結果當作需重驗。確認是舊結果才執行遷移命令（記錄者 `legacy`）。

## 面板與 Viewer

- Checklist 面板：失效的結果（沒有記錄者、內容改過、早於最近一次釋放）照「還沒記錄」顯示：標記是空框加警示色外框，不顯示 ✓，也不改成 `[!]`（失效不是不通過，標 `[!]` 會把沒壞的項目送去修正）；工作項目標記、進度數字與先後鎖都用有效狀態；點擊從空框開始，等於重新記錄；檔案上的舊標記保留到重新記錄為止。
- Checklist 面板：顯示每項的標籤、記錄者與 `[acceptance]` `[!]` 的原因；依先後規則鎖住還不能記的標籤檢查（`[acceptance]` 等自驗、`[manual]` 等他驗）；`[acceptance]` 可點，但先跳出確認；提供「只顯示我能操作的檢查」。
- Report 子項狀態：未開始、執行中、等待中、待他驗、待使用者（含爭議）、條件待修、需修正、完成，依〈子項狀態（推算）〉。等待中的畫面見〈等待〉。

## 已知限制

- 身分是自報的：actor、session 與記錄者欄位都由寫入端提供，刻意偽造擋不住；這套設計擋的是誠實的失誤。
- 上下文是否獨立無法由程式驗證：CLI 只比對 `session_id`。執行者換一個 ID 在原上下文自己驗收，CLI 看不出來，由〈獨立驗收上下文〉的規則約束。CLI 從活動紀錄擋下建立者（`created`）與執行者；代為修改條件的 session 沒有活動事件，同樣只靠規則。
- 不標檢查由執行者直接編輯檔案，系統不知道是誰勾的，與現況相同。
- 驗收者直接修改程式而不接手子項時，系統看不出來。
- 同一個模型換 session 驗收，仍可能帶著同樣的理解偏差；他驗的效果主要來自規劃時寫好的條件。
- 時間分析改用推算的完成狀態，但只在 Report 改動時重算；只改了 checklist 時，要等下一次 Report 寫入或明確執行 `analyze` 才更新。
- 先後規則只在寫入時強制。三份舊 checklist 把未完成的 agent 檢查和 `[manual]` 放在一起（Web `ui-workflow`、TaskProgress `report-cli-update`、`third-party-checklist-write`），它們的 `[manual]` 要等 agent 檢查完成才能再記錄。

## 實作項目

對應 Report agent-workflow 卡的子項：

1. `checklist-acceptance-chain`：checklist 格式。登記 `[acceptance]`，未登記的標籤拒絕；標籤檢查的記錄者與內容指紋欄位，讀取時比對；標籤檢查自動等待不標的工作項目；`checklist validate` 對應錯誤。
2. `acceptance-checklist-write`：標籤寫入。`checklist request` 帶 actor 與 `session_id`；從綁定子項取得執行者；權限與先後檢查；`[acceptance]` `[!]` 的原因（實作不符／條件不符）與次數；記下記錄者、時間與指紋。
3. `acceptance-report-cli`：Report CLI 與活動紀錄。`released`、`disputed` 事件（`item.event`）與保留規則（Python、JS、schema 三處）；他驗流程缺 `session_id` 拒絕；狀態推算在 C#（`report get` 的 `derived_state`、時間分析）與 JS（Viewer）兩處一致。Python 不解析 checklist Markdown，所以不另做一份。
4. `acceptance-checklist-panel`：Checklist 面板。標籤與記錄者顯示、標籤檢查鎖、`[acceptance]` 覆寫確認、只顯示我能操作的檢查。
5. `acceptance-viewer-states`：Report 子項顯示八種推算狀態。
6. `acceptance-skills`：skill。改寫 checklist-round、agent-executable-items 與 ItemActivityLog（依〈取代的現行規則〉）；新增 Claude skill `/task-progress-items`；同時改共用索引的可執行項目那一列，並檢查 Claude 可達的其他路由不會繞過入口（〈入口邊界〉）。
7. `item-waits`：等待。子項的等待欄位（schema、Report CLI 寫入、環的拒絕）、跨 scope 讀取被等子項的狀態、等待中的推算與畫面（收合標籤、展開後的連結）。
8. `checklist-legacy-migrate`：遷移。遷移命令；新規則上線時，對所有已登記 scope 執行一次（2026-10-22 統計 UX、Web、TaskProgress 有 27 份 checklist、46 個 `[manual]` 結果，其餘 scope 執行前再統計）；執行前檢查各 repo 是否有他人未提交的工作，只提交遷移改到的檔案。
9. `acceptance-flow-trial`：端到端試跑，照〈流程紀錄〉的情境各走一次。

## 驗收

- 〈流程紀錄〉的每個情境，在實作後實際走一遍，每一步的推算狀態與佇列挑選都和紀錄一致。
- `checklist validate`：未登記的標籤與沒有記錄者的標籤結果回非零並指出行號。先後規則在寫入時強制，validate 不追溯舊結果。
- 指紋：記過結果後直接改檔案修改標籤檢查的 `Action`／`Expect`，重新讀取時該結果顯示「需重驗」。
- 沒有記錄者：直接改檔案替標籤檢查打勾，`checklist validate` 失敗並提示遷移；面板照常開啟，該項顯示「需重驗（沒有記錄者）」。
- 遷移：遷移後，原有 `[manual]` 結果照常顯示為完成，記錄者為 `legacy`；遷移命令對已有記錄者的結果不做任何改動。
- 寫入：與任一執行者相同的 session 寫 `[acceptance]` 被拒；agent 寫 `[manual]` `[x]` 被拒、寫 `[!]` 沒有 `Observed` 被拒；未綁定子項時寫入被拒；他驗流程缺 `session_id` 被拒；使用者經面板改 `[acceptance]` 會先確認。
- Report CLI：連續寫入多筆其他事件後，`created`、`started`、`takeover` 仍在；`report get` 與時間分析的狀態和 Viewer 一致。
- 先後：自驗未完成時寫 `[acceptance]` 被拒；`[acceptance]` 未全部通過時寫 `[manual]` 被拒，面板上鎖住。
- 條件不符：標「條件不符」推算為條件待修；修改條件後原 `[!]` 失效、回到待他驗；`disputed` 或同一項第二次「條件不符」推算為待使用者（爭議）；提出問題的驗收者不能修改該條件。
- 入口：對 Claude 說舊短語或只給項目 ID 時，不建立項目也不執行，只回對應的命令；調整既有 checklist 時不建立項目；其他 agent 用舊短語仍照現有流程。
- 等待：被等子項未完成時顯示等待中、`run` 不挑；跨 scope 的被等子項完成後自動解除；形成環的宣告被拒；收合時子項高度不變，展開後連結可點、開啟對方卡片並置頂。
