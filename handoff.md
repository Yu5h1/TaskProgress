## Architecture and contracts (current, load-bearing)

- **UI host boundary:** `viewer/assets/ui-host.js` — `registerUiAdapter`, `useUiAdapter`, `createUiView(region, target, props)` returning `update`/`destroy`. Only plain data and callbacks cross; the host never touches rendered nodes (`tests/ui-host.test.mjs` asserts the source has no DOM access, no framework name). One adapter active at a time — registering a second does not take over. Bundling `ui-host.js` into the preview bundle instead of keeping it external gives the bundle its own adapter registry, so registration silently misses the instance `app.js` imports (zero cards, no error) — `rollupOptions.external` + `output.paths` must keep it external.
- **Regions are named:** an adapter declares which regions it implements; mounting an unclaimed region throws. Current Svelte adapter (`viewer-adapter.svelte.js`) covers `task-list`, `status-overview`, `status-filters`, `project-progress`, `mode-toggle`, `save-bar`, `add-control`, `diagnostics`, `scope-directory`, `theme-control`, `time-summary-button`, `time-dialog`, `time-settings`, `delivery-risk-preview`, `delivery-save-confirmation`. **The committed bundle (`viewer/assets/viewer-ui.js`) is a separate artifact from this source file** — registering a region in `viewer-adapter.svelte.js` does nothing for the production Viewer until `npm run viewer:ui:build` regenerates the bundle; the adapter throws `不支援 region「...」` at runtime otherwise, and nothing in the test suite catches it (tests read sources, not the bundle — see Blockers).
- **Architecture boundary:** `editor-core/` + `ui-components/` + `local-service/` — one component set serves both preview and edit; mode only decides whether a field is editable, like an `InputField` toggling `editable`. Public deployments stay read-only through build-time splitting (packaging), not a second implementation (architecture). Edit-only affordances (delete, save bar, add controls) are states of the shared component, not a second interface.
- **Editor presentation layering:** `viewer/assets/editor-presentation.css` is the shared **geometry** contract, colour-free by contract (`tests/editor-presentation.test.mjs` asserts no `color`/`background`/`box-shadow`). `viewer/assets/styles.css` is the shared **theme** stylesheet (the Svelte bundle imports it via `@editor/styles.css`); cross-host colour rules key on the shared class. - Two Svelte gotchas specific to how this project mounts components imperatively (`mount(Component, {props: someExternalState})`, the pattern every `ui-host.js` region uses):
  1. A bare `$:` block, or an action's `update(prop)` parameter, reading a legacy `export let` prop re-evaluates once after mount and then silently stops seeing further changes — even though the same prop keeps driving ordinary template expressions (`{title}`, `{#if kind==="item"}`) correctly. Fix: make the dependent DOM structural (`{#if open}<dialog use:openOnMount>`) instead of imperative, since Svelte's own block (dis)connection is driven by the template reactivity that already works.
  2. A template call expression hides what it reads — `class={dropClass(filter)}` never re-ran when a handler set `dropTarget` elsewhere. Pass reactive state as an argument (`dropClass(filter, dropTarget)`) to make the dependency visible to the compiler.
  3. A `<select>` bound with `value={...}` is uncontrolled — the reader's own selection never reaches component state, so a cancel handler that reassigns the same prop is a no-op. Use `bind:value`.
  4. Legacy `$:` statements are pre-effects, not lazy deriveds, so anything persisted on an event must be recomputed from source state at commit time, not read from an already-rendered derived value that may not have run yet in the same task.
- **Browser cache trap:** `viewer/assets/viewer-ui.js` has a stable filename with no cache-busting query, so a rebuilt bundle can keep serving from cache through a forced reload. `performance.getEntriesByType("resource")[...].transferSize === 0` is the tell; serving on a fresh port is the fastest fix.
- **Bundle staleness CI guard:** `notify-docs.yml`'s `verify-bundle` job runs `npm ci`, rebuilds with `npm run viewer:ui:build`, fails if `git diff` shows the bundle changed, then runs the suite; `notify` depends on it. Trigger paths include `experiments/editor-svelte-spike/**`, `package.json`, `package-lock.json`. Unproven in CI per Blockers above.
- **Preview bundle must stay flat** at `viewer/assets/viewer-ui.js`: the docs Pages artifact copies `viewer/index.html` + `viewer/assets/`, and a subdirectory only survives if that copy is recursive (unverifiable from this repo). Vite's `outDir` is `viewer/assets` with `emptyOutDir: false` (`true` would delete hand-written sources). ## Product/UX spec (current shape)

- Viewer: compact centered progress-dashboard layout, vertically dense. Every task card shows a top-right fraction, no task percentage. Status pills reorder without an edit mode; ordering syncs summaries, whole cards, and the pending/completed panel order, persisted as a browser-local preference. Task/item priority: independent optional integers `0..4`, single source is `viewer/assets/priority-policy.js` (bounds, legacy fallback and creation default `4`, labels 立即／優先／一般／次要／未指定, formatting, tones); missing legacy values and new data project as badge-free `4`. - Progress precedence: a task with `completed_items`/`pending_items` derives its card fraction and the project total from those visible items; explicit `progress` is only the fallback for item-less tasks.
- Themes: `system` follows `prefers-color-scheme`; explicit light/dark/custom persist in `localStorage` under `task-progress.theme.v1` (`version: 1` required). Custom palettes: eight semantic core colors, inherit status colors from a light/dark base, validate `#RRGGBB`, warn below 4.5:1 contrast. A pre-CSS bootstrap applies saved preference before paint.

## Report/workspace model

- The same report schema can describe a multi-project workspace, a project, or a narrower component. Viewer/Launcher render one selected scope and do not infer hierarchy; report-generation resolves hierarchy from the target scope, its `tasks.md`, canonical routes, and child reports/handoffs.
- A workspace report is a curated portfolio view — it may mix direct tasks, whole child scopes, and selected child deliverables, but must not recursively scan directories or treat unrelated child items as equal-weight. A workspace scope may validly have no handoff of its own.
- Cross-scope drill-down now has an approved design that nothing implements yet: `plan.md#report-指路任務卡與單層-scope-導航` (approved 2026-08-18). A pointer card stores only `id`, `title` and `report_ref.scope_id`; everything shown is derived from the target report at read time, one level deep. Deterministic aggregation beyond that one level, and stale-roll-up detection, remain unprovided by the Viewer, Launcher and schemas.
- Routing/fallback rule detail: `plan.md#任務入口與報告更新規則`. Local editing design detail: `plan.md#本機任務編輯-draft-01`, `#editor-框架化與大改-draft-01`, `#交付日編輯與敏感修改歷史-draft-01`.

- Primary source: `src/TaskProgress.Cli/` — report validation, local scope store, browser opening, `task-progress://` install/uninstall.

- Commands: `start`, direct report folder, `open --scope`, `scope add/remove/list`, `service status/stop`, `protocol install/uninstall`. `start` validates every stored scope before service mutation, registers all reports, removes stale routes, writes a path-free catalog, opens the Viewer root. `scope add <folder>` derives kebab-case scope from folder name.
