# TaskProgress handoff

- Canonical status entry: task status and progress are referenced by Task ID in `report.json`; Developer next steps, blockers, decisions, and routes are referenced by the same ID in `report.dev.json`. Do not duplicate the referenced content here.
- Active claim: none.
- Routing and fallback rule: see `plan.md#任務入口與報告更新規則`. This handoff remains the canonical coordination entry while using reports as referenced structured records.
- Report scope model: the same report schema may describe a multi-project workspace, a project, or a narrower component. The Viewer and Launcher render one selected scope and do not infer hierarchy; the report-generation workflow resolves hierarchy from the target scope, its `tasks.md`, canonical routes, and child reports or handoffs.
- Workspace roll-up: a workspace report is a curated portfolio view and may mix direct workspace tasks, whole child scopes, and selected child deliverables. Each routed card must make that coverage clear; do not recursively scan directories, copy every descendant item, or treat unrelated child items as equal-weight portfolio progress. A workspace scope may validly have no handoff of its own.
- Capability boundary: Agent report generation performs the current cross-scope synthesis. Deterministic child-report aggregation, drill-down, or stale-roll-up detection would require explicit machine-readable parent/child coverage and is not provided by the current Viewer, Launcher, or schemas.
- Extension-module design: `Documentation/ExtensionModuleArchitecturePlan.md` is the Draft 0.1 architecture source. It keeps `report.json` stable, treats the existing hard-coded time sidecar as the first reference module, proposes optional manifest discovery plus trusted built-in Viewer/Launcher registries, forbids report-directed executable code, and requires per-module validation and failure isolation. Implementation status and next steps are referenced by the `extension-modules` entries in both reports.
- Local editing design: see `plan.md#本機任務編輯-draft-01`, `plan.md#editor-框架化與大改-draft-01`, and `plan.md#交付日編輯與敏感修改歷史-draft-01`; implementation state and the active Editor Core extraction step are referenced by the `local-task-editing` entries in both reports.

Public/static hosting remains read-only. The mode control is one pressed-state toggle, deletion uses explicit text instead of `×`, Dialog close glyphs are centered, and the save action is forced to a dark-blue background with white text. Each task card has exactly one child-item `＋` at the bottom; it always creates a `pending_items` entry, independent of the displayed status order. Existing item-time buttons remain visible during global task editing but are still read-only estimate-detail actions; secure estimate-source editing remains a separate cross-file transaction task. Work-capacity editing no longer has its own edit/cancel state: global edit places the capacity form first in the panel under the compact `設定` heading, `重新計算` changes only the in-memory preview and global dirty state, global save stages the local override and rolls it back if report save fails, and global preview restores the persisted capacity profile. Structural changes disable stale task/item/project time projections until save and reanalysis, while description/priority edits preserve valid estimates. - Viewer UX: the Viewer uses a compact, centered progress-dashboard layout. Status pills can be reordered without entering an edit mode, and the ordering synchronizes summaries, whole task cards, and the pending/completed panel order while persisting as a browser-local view preference. - Scope rule: `?scope=<id>` resolves to `../reports/<id>/report.json`; explicit `?report=` wins. On exact loopback hosts (`localhost`, `127.0.0.1`, or `::1`), scope also attempts the sibling `report.dev.json`: HTTP 404 is a normal base-only result, while an existing valid file is merged automatically. Public origins never auto-load Developer data. Explicit `?dev=<path>` still works and `?dev=none` disables the loopback overlay. The same base-report relative rule works for the source `viewer/`, nested public deployments, and the localhost root.
