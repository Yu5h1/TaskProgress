# TaskProgress handoff

- Canonical status entry: task status and progress are referenced by Task ID in `report.json`; Developer next steps, blockers, decisions, and routes are referenced by the same ID in `report.dev.json`. Do not duplicate the referenced content here.
- **Top priority (2026-08-05, user decision): one UI source. A screen element visible in more than one place may have only one implementation.** This outranks feature work, parity patching and further migration. Adding a second implementation of an existing element is not acceptable even when it is faster, and neither is a configuration knob that lets two hosts render the same element differently — a knob is a drift source, so consolidation deletes it rather than aligning its value. When a shared element and a host-specific need collide, the host supplies data and callbacks and the shared component keeps the markup. Everything below is measured against this rule.

- Report scope model: the same report schema may describe a multi-project workspace, a project, or a narrower component. The Viewer and Launcher render one selected scope and do not infer hierarchy; the report-generation workflow resolves hierarchy from the target scope, its `tasks.md`, canonical routes, and child reports or handoffs.

- Svelte legacy-mode reactivity trap: a template call expression hides what it reads, so `class={dropClass(filter)}` never re-ran when the drop target moved even though the handler was setting it. Passing the state in as an argument — `dropClass(filter, dropTarget)` — makes the dependency visible to the compiler. Components in this project use `export let` (legacy mode), so any helper called from markup must take its reactive inputs as parameters.

Serving the repo on a fresh port is the quickest way to confirm a fix against the new bundle.

- UI host boundary (2026-08-04, plumbing complete, wired into the Viewer): `viewer/assets/ui-host.js` defines the swappable-UI contract — `registerUiAdapter`, `useUiAdapter`, `createUiView(target, props)` returning `update`／`destroy`. - Architecture boundary corrected (2026-08-04): `plan.md#架構邊界` previously listed `editor-ui/` as framework components and `viewer/` as "維持輕量唯讀，不要求載入 Editor 框架". Those two rules together made one shared component set impossible by construction — preview could never use the editor's components, so every common element had to exist twice, and the iframe overlay was the consequence rather than a shortcut. The boundary now reads `editor-core/` + `ui-components/` + `local-service/`, where one component set serves both modes and the mode only decides whether a field is editable, the way an InputField toggles `editable`. Public deployments stay read-only through build-time splitting, which is a packaging concern, not an architectural one. Decision rule: if a screen element is visible in both preview and edit, it may have only one implementation; edit-only affordances (delete, save bar, add controls) are states of that same component, not a second interface.
- Editor presentation layering (2026-08-04): two files, two roles, both loaded by every host. `viewer/assets/editor-presentation.css` is the shared **geometry** contract and is colour-free by contract — `tests/editor-presentation.test.mjs` asserts it contains no `color`, `background` or `box-shadow`. `viewer/assets/styles.css` is the shared **theme** stylesheet, which the Svelte bundle also imports through `@editor/styles.css`; shared colour rules that must match across hosts belong there, keyed on the shared class (for example `.editor-mode-dock[aria-pressed="true"]`). Putting colour into the geometry file fails the suite; that is intentional and should not be relaxed.
- Mode-toggle pressed state: the toggle uses a tint (`--blue` on `--blue-soft`), not a solid accent fill. The Svelte surface previously used `color: white` on `background: var(--blue)`, which in the dark palette is white on a light blue and measured about 2.3:1. The shared rule now measures 6.92:1 in dark and 5.47:1 in light on both surfaces.
